# RST-001 — Estándar del Repositorio (Repository Standard)

---

## 1. Propósito
El propósito del **RST-001** es definir los principios y directrices de ingeniería que regulan la organización, evolución, validación e integridad de los repositorios gobernados por **KODE**. El repositorio no es un mero contenedor de código, sino el Activo de Conocimiento institucional primario donde coexisten la lógica ejecutable, las decisiones, directivas y la memoria histórica del proyecto.

## 2. Filosofía del Repositorio
*   El repositorio representa la **memoria histórica inmutable** del proyecto.
*   Todo el desarrollo de software y la gobernanza organizacional deben coexistir bajo el mismo control de versiones.
*   Cualquier código o documentación no registrada formalmente en el repositorio se considera no existente para la organización.

## 3. Principios del Repositorio
*   **Single Source of Truth (SSOT):** Un único lugar canónico para cada elemento de información.
*   **Conocimiento Primero:** La documentación metodológica y técnica es tan importante como el código ejecutable.
*   **Trazabilidad:** Cada cambio de estructura o código debe ser auditable en el historial.
*   **Reproducibilidad y Mantenibilidad:** Estructuras lógicas y limpias orientadas a la longevidad del software.
*   **Gobernanza Humana:** Cambios de estructura mayor requieren la aprobación del rol humano responsable.

## 4. Organización del Repositorio
KODE favorece la organización lógica sobre las carpetas arbitrarias:
*   **Source Code (Código Fuente):** Separado lógicamente por aplicaciones y paquetes compartidos.
*   **Knowledge Assets (Activos de Conocimiento):** Agrupados jerárquicamente por niveles de gobernanza (Constitución, Biblia, Estándares).
*   **Statements y Prompts:** Estructuras dedicadas para la catalogación y trazabilidad de las instrucciones a IAs.
*   **Configuración y Automatización:** Declarada de forma explícita e independiente del entorno de ejecución.

## 5. Organización del Conocimiento (Knowledge Organization)
El repositorio mapea de forma relacional el conocimiento:
*   La **Constitución** gobierna el marco del **KAC** y **KGG**.
*   Las **Declaraciones (STM)** habilitan los **Prompts (PRM)** que a su vez evolucionan el **Código Fuente** y la **Biblia del Proyecto**.
*   Las discrepancias del sistema alimentan la **Deuda de Conocimiento (KD)** para su oportuna resolución.

## 6. Estándares de Documentación
*   **README General:** Indexa el repositorio completo.
*   **READMEs de Directorio:** Obligatorios en carpetas principales, actuando como mapas de navegación.
*   **Documentación Técnica:** Debe residir junto al código fuente que describe, facilitando su actualización en el mismo commit.

## 7. Metadatos del Repositorio
En cumplimiento de **STM-0002**, cada activo de documentación debe incorporar su cabecera de metadatos YAML. El repositorio mantendrá de forma centralizada el [Índice de Metadatos](../KODE_METADATA_INDEX.md) para habilitar herramientas automáticas de indexación y navegación.

## 8. Principios de Control de Versiones
Independientemente de la tecnología de control de versiones utilizada (Git, Mercurial, etc.), se deben cumplir las siguientes directrices:
*   **Preservación Histórica:** Prohibido reescribir historiales compartidos que eliminen la trazabilidad de decisiones previas.
*   **Rendición de Cuentas:** Cada aportación debe identificar un autor humano responsable.
*   **Modificaciones Controladas:** Cambios estructurales deben ser aprobados y documentados en el changelog general.

## 9. Gobernanza del Repositorio
*   **Owner (Propietario):** El *Methodology Owner* o *Project Director* (humanos) aprueban cambios estructurales mayores de carpetas.
*   **Steward:** El *Project Librarian* es el custodio operativo de la sanidad del repositorio, sus índices y referencias cruzadas.

## 10. Preservación del Conocimiento
El repositorio debe contar con mecanismos para evitar la fuga de información:
*   Los prompts y ADRs actúan como la memoria del "por qué" se tomó una decisión técnica.
*   Se prohíbe basar la lógica del proyecto en discusiones orales o chats externos no consolidados en el repositorio.

## 11. Calidad del Repositorio
Se evalúa bajo los criterios de:
*   **Navegabilidad:** Enlaces relativos funcionales entre todos los activos.
*   **Consistencia:** Ausencia de redundancias o contradicciones documentales.
*   **Escalabilidad:** Estructura que permite añadir módulos y activos de conocimiento sin romper la jerarquía inicial.

## 12. Validación del Repositorio
Se alienta la implementación de herramientas automáticas (linters documentales, scripts de verificación) para detectar:
*   Enlaces de Markdown rotos.
*   Falta de metadatos obligatorios en activos nuevos.
*   Activos huérfanos sin relación `Governed By`.
*   Registros de Deuda de Conocimiento (`KD`) desactualizados.

## 13. Antipatrones (Anti-Patterns)
*   **Conocimiento Externo:** Almacenar especificaciones de diseño en wikis externas o servicios en la nube no controlados por versiones en este repositorio.
*   **Hitos Indocumentados:** Integrar ramas de desarrollo sin actualizar el Changelog del repositorio.
*   **Acoplamiento de Plataforma:** Diseñar la estructura o flujos de trabajo asumiendo características exclusivas de un proveedor de hosting de repositorios (GitHub/GitLab).

## 14. Evolución Futura
La estructura de este estándar está diseñada de forma flexible para admitir nuevos lenguajes de programación, frameworks y herramientas de automatización futuras sin alterar las directrices de gobernanza supremas definidas por la Constitución de KODE.

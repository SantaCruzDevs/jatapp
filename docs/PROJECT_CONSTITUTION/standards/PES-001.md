# PES-001 — Estándar de Ingeniería de Prompts (Prompt Engineering Standard)

---

## 1. Propósito
El propósito del **PES-001** es formalizar la Ingeniería de Prompts dentro de **KODE** como una disciplina técnica gobernada. Establece las directrices para la creación, mantenimiento, versionado y control de calidad de las instrucciones enviadas a los agentes cognitivos, tratándolas como **Activos de Conocimiento (PRM)** oficiales y no como simples interacciones efímeras.

## 2. Definición de un Prompt
*   **Prompt (Instrucción de IA — PRM):** Un artefacto estructurado de entrada gobernado por KODE que define metas, contextos y restricciones para guiar el comportamiento de un agente. Preserva conocimiento institucional reutilizable.
*   **Conversación:** Secuencia temporal e interactiva de chat que se considera transitoria.
*   **Diferenciación:** Las conversaciones expiran tras su uso operacional, mientras que los Prompts oficiales persisten en el repositorio y guían el ciclo de vida del desarrollo.

## 3. Principios de Ingeniería de Prompts
*   **Reutilización:** Diseñados para ser modulares y aplicables a múltiples contextos.
*   **Claridad:** Instrucciones declarativas con nula o mínima ambigüedad técnica.
*   **Trazabilidad:** Cada prompt oficial debe estar enlazado a un cambio de código o decisión organizativa.
*   **Gobernanza Humana:** Solo un rol humano aprueba la integración final de un prompt como activo gobernado.

## 4. Clasificación de Prompts
Los prompts oficiales se clasifican según su propósito:
1.  **Gobernanza y Estrategia:** Promulgan decisiones constitucionales o identitarias.
2.  **Arquitectura y Diseño:** Guían el desarrollo de flujos técnicos y patrones.
3.  **Implementación:** Instruyen en la generación de código y software ejecutable.
4.  **Validación y Pruebas:** Parametrizan pruebas automatizadas e inspección sintáctica.
5.  **Documentación:** Estandarizan registros de cambios e índices.
6.  **Operación y DevOps:** Gobiernan la infraestructura y despliegue.

## 5. Ciclo de Vida del Prompt
Un prompt progresa por los siguientes estados:
```
Idea ➔ Draft (Borrador) ➔ Review (Revisión) ➔ Approved (Aprobado) ➔ Published (Publicado) ➔ Mantenido ➔ Depreciado ➔ Archivado
```

## 6. Gobernanza de Prompts
*   **Ownership:** Cada prompt oficial debe tener un único propietario humano asignado en sus metadatos.
*   **Stewardship:** El *Project Librarian* custodia su correcta catalogación y control de versiones en el repositorio técnico.

## 7. Metadatos de Prompts
En estricto cumplimiento de **STM-0002**, todo archivo de prompt oficial debe comenzar con la cabecera YAML obligatoria detallando su ID, título, estado de aprobación, dependencias a otros activos y ciclo de revisión.

## 8. Relación con otros Activos de Conocimiento
*   Los Prompts (PRM) se derivan de directivas oficiales de Declaraciones (STM) o Decisiones de Arquitectura (ADR).
*   Ejecutan la evolución de la Biblia del Proyecto o de la base de código técnico.
*   Sus desvíos documentales u obsolescencias alimentan el registro de Deuda de Conocimiento.

## 9. Directrices de Diseño de Prompts
Al construir un prompt oficial en KODE se debe asegurar:
*   **Responsabilidad Única:** Un prompt resuelve una única meta o tarea de ingeniería específica.
*   **Comportamiento Determinista:** Reducir variables ambiguas para que el agente devuelva resultados consistentes ante las mismas entradas.
*   **Modularidad:** Evitar prompts sobrecargados; preferir la secuenciación o concatenación de prompts simples.

## 10. Requerimientos de Trazabilidad
Cada prompt debe registrar explícitamente:
*   El entregable esperado y el agente especializado objetivo para el cual fue optimizado.
*   La declaración organizacional (`STM`) o registro técnico (`ADR`) en el cual se apoya la instrucción.

## 11. Deuda de Prompts (Prompt Debt)
Se define como la acumulación de ineficiencias o brechas en las instrucciones del proyecto. Incluye:
*   Prompts duplicados o redundantes.
*   Instrucciones dependientes de plataformas de chat específicas.
*   Prompts obsoletos que no reflejan la versión actual del código o la arquitectura.
*   Prompts sin propiedad humana declarada o desconectados de directivas.

## 12. Criterios de Calidad de Prompts
Los prompts serán evaluados mediante revisiones sintácticas y semánticas enfocadas en la **Claridad**, **Mantenibilidad**, **Testabilidad** y **Consistencia** respecto a la Constitución del proyecto.

## 13. Seguridad de Prompts
*   **Acceso y Exposición:** Prohibido inyectar credenciales hardcodeadas, tokens de API o datos confidenciales de usuarios directamente en las instrucciones.
*   **Integridad:** Protección contra técnicas de inyección que alteren las instrucciones constitutivas de los agentes.

## 14. Buenas Prácticas
*   Buscar la modularidad y parametrización de variables en las entradas del prompt.
*   Documentar detalladamente la motivación e historial de evolución del prompt en su changelog.
*   Priorizar la reutilización de plantillas de prompts validadas en sprints anteriores.

## 15. Antipatrones (Anti-Patterns)
*   **Instrucciones Efímeras:** Confiar procesos estratégicos a diálogos no guardados en el control de versiones.
*   **Dependencia del Proveedor:** Diseñar prompts con sintaxis o hacks que solo funcionan en una interfaz web de un único vendor, rompiendo la independencia tecnológica de KODE.
*   **Metadatos Inexistentes:** Prompts sin cabecera de gobernanza, imposibles de auditar o catalogar automáticamente.

## 16. Evolución Futura
A medida que se desarrollen nuevos marcos de interacción cognitivos, este estándar se actualizará para dar cabida a nuevos tipos de agentes, conservando la independencia de tecnologías de IA subyacentes.
